# book_qa

The book lane of the coder workflow. A story that touches a service with an executable book (`services/<name>/service.py` under the book root when the repository keeps its book, `services/<repo>/<name>/service.py` in the artifacts folder) has that service judged by a run of the book. The scenario QA in `qa/` is a separate lane. The main loop hands off to this one first, and enters the scenario QA only when no service of the story has a book. Both return a `QaFlowResult`.

The lane costs one seat turn and one end review turn. The verdict costs no model call. A story with no covered service ends here as `passed` with no agent call and no stack.

## How a story's book pass settles

1. `start` lists the story's covered services: the declared ones that have a book, then every other service with a book whose app source the story's commits changed. In a workspace of several repositories, the lane reads each service's code from the repository that holds it: the one whose `agents.yml` declares the service, otherwise the first of the workspace that holds the book, with a warning when several do. A service no repository holds sends the run to the operator. The selection runs as `ostler book stale --since <story base>`, and `--story <id>` too when a commit carries the trailer `Story: <id>`, otherwise the range. The story base is the commit its own work started from, read in each holding repository. It then leases a copy of the stack and brings it up. A stack that is not up goes to the operator, never to the seat. A `book-qa.json` in the spec dir holds the calls the plans selected, so a second visit for the same story goes straight to `check`.
2. `work` runs the `qa-book` seat. It brings each covered book up to the story's claims and reports a finding for each claim the app does not meet. A `blocked` reply asks the operator.
3. `check` runs `ostler book check` for each covered service. It then runs `ostler book affected` for the service, with `--app` set to the repository that holds its code, the story base of that repository as `--since` and, when a commit reachable from HEAD carries the trailer `Story: <id>`, with `--story <id>` so that only the story's own commits and the uncommitted work are read (the lane logs `the selection of <service> reads the N commit(s) of story <id>`, or `no commit carries 'Story: <id>'` and reads the range since the base), which selects the plays from the diff of the app's code and of the book's own files, with no app and no model call. Exit 2 of the selection, or a changed file or function no element of the book names, goes back to the seat, and nothing is played until it is fixed. A plan of `none` or `empty` plays nothing for that service. When the report carries the direct fields, the lane plays the direct journeys first by `--partial --journey <title>`, on fresh data. It then plays `direct_only` by `--only <calls>`. The two plays are separate because the two flags combine as AND, and they share one `book_play_minutes` budget per service. A first play that fails or hits the limit behaves as before. A calls play that hits the limit after green journeys is recorded as `- owed: the direct calls did not finish within <n> min`, and the check goes on. The reached selection is never played, and `qa-plan.md` lists its counts and its top five causes as owed to the scheduled whole play. A report with no direct fields falls back to `only`, then `by_journey`. A story with no direct play laps to the seat when it changed files. A plan of `whole`, or a pass that changed a shared part of the book, never plays the whole book: the service plays what the selection still names directly, and the reason the selection could not narrow is listed as owed to a scheduled whole play, which runs outside any story. Before each play the lane logs what it will play and its limit. Every play reloads the data first (`--fresh-data` on the first play of a service), runs against `--copy <lease>` and ends within `book_play_minutes` minutes (15 by default, a workflow parameter of the coder), or exits 3. Exit 1 or 2 of a play goes back to the seat with the tail of the output. Exit 3 means the environment could not be judged, and it asks the operator without a finding or a lap. When no service plays anything and one has an owed entry, the seat gets a lap that lists the owed reasons: the change could not be narrowed to any play, so state it in an element a play reaches. When no service plays anything, none is owed and the story changed files, the seat gets a lap: the book does not state what the story changed. A story that changed nothing passes with no play. Each pass of `check` writes `qa-plan.md` in the spec dir from code: the plan, the change read (`- change read:`, the story's commits or the range), its reason, the calls, the journeys, the uncovered list, the changed and unjudged file counts and the exit of each play, a line per service of what is owed to the scheduled whole play (the first 10 reasons, then `and N more`), and a top line saying whole plays are never run for a story. The reports of the plays land under `qa/book` in the spec dir.
4. The end review runs when every play passed and the seat reported no finding. `check` ends there, and the review runs in its own state, `review`, so a resume of the run does not play the books or run the review twice. The `qa-review` turn reads the story's acceptance criteria, functional then non-functional, numbered by the workflow, with the `qa-plan.md`, the play reports, the claims the seat listed as `unreached` and the earlier evidence in the spec dir. It gives each criterion one verdict: `played`, `tested`, `recorded`, `checked`, `unobserved` or `unmet`. It may run bounded extra checks, one item at a time, never a whole dataset, a whole book or production, each under 5 minutes. It edits no tracked file and writes no file. The turn runs on its own session under `review_minutes` minutes (20 by default, a workflow parameter of the coder). The code writes `qa-review.md` in the spec dir from the validated verdicts. A review that gives no verdict for a criterion gets one more turn with the missing numbers, and then the operator is asked. A review cut at the limit asks the operator, and the answer runs it again on the same session. A story with no criterion skips the review. A story whose seat reported a finding skips it too, because it goes back to its developer anyway. An `unmet` verdict ends the lane as `refix` with one finding per unmet criterion and stamps no book. The finding is not written to `book-qa.json`, so the next visit reviews again. An `unobserved` verdict does not fail the story. The lane records it in the `unobserved` field of `book-qa.json`, in `qa-review.md` and in a warning, and the scenario QA lane owes it as a claim.
5. The `land` state runs the rest. With no seat finding and no `unmet` verdict, it runs `ostler book verified` for each covered service whose book was current when the story started, so the book records the app commit it was judged at. The stamp passes `--story <id>` under the same condition as the covered services. When other commits since the verified commit left code no element names, `verified` prints `not stamped`, the lane logs it and sends no lap. Only the story's own unnamed code goes back to the seat. The stale report against the book's verified commit must name only entries the report since the story's base also names. A book already current, a book with no verified commit and a book that was behind before the story are left alone and sent no lap, so a second visit stamps nothing twice and the catch-up flow keeps the older changes in view. A refusal goes back to the seat with the output. Then the lane lands the changed paths under each covered `services/<name>/` as one `test` commit with the story's footer, and writes `book-qa.json`. A changed product path outside those folders refuses the commit and goes back to the seat. The lane ends as `refix` with the seat's findings and the unmet criteria, or as `passed`. A finding stops the story even on a green run, because a declared defect makes the run green by design. A record that holds a finding is never replayed. The story goes to the seat again with the earlier findings as its report, and the seat judges each against the fixed app: it reports again only what the app still fails, and states the rest in the book as current behaviour. The record is rewritten from what the seat reports.

Checks that still fail after three repair turns park the run at the operator gate.

# Building a whole service's subgraph

Read this when you are modelling an **entire service** — its surfaces, elements, behaviours,
concepts, flows and formats — as a conformant subgraph under `docs/features/<service>/`, rather
than merging one story's delta. The format itself, the three content rules and the
scaffold→author→fmt→doctor loop are in the parent `SKILL.md` and are assumed here; so is the type
you are about to build (`references/node-types/<type>.md`) and `references/bullet-grammar.md`.

Two playbooks converge on the *same output* and share the *same mechanics*. Only the **input**
differs:

- **From a description** — a human hands you intent (a feature brief, a mockup, "here is the
  screen I want"). Design-time, before the code exists. The step-by-step loop is
  [from-description.md](from-description.md).
- **From existing code** — you read a running codebase and recover the graph it already
  implements. Archaeology-time. The step-by-step loop is [from-code.md](from-code.md).

Do not invent a third way. Both end at the same convergence gate below. Read the playbook you are
in — the summaries here are not the procedure.

The bullets differ in one place only. **From a description**, leave `code:`/`tests:` as **stubs**;
they are grounded later, when the code exists, and a fabricated `path::symbol` is worse than an
empty one. `verify:` is the opposite — it is the *most* writable bullet at design time, because the
observation that would prove a behaviour is knowable before the code producing it exists. **From
code**, you fill `code:`/`tests:` with the real `path::symbol`, because it is there to read.

> The greenfield pass is the **okf-builder** workflow's job: emit the skeleton at design time so
> the coder inherits a target rather than a blank page. The **author** workflow never runs either
> playbook — it reads the book to ground its stories and is forbidden from writing to it. The
> **coder** workflow runs the from-code pass after implementing a story, and so does dogfooding a
> service: walk the code, land the subgraph, prove it green.

## How any surface decomposes — six layers

Whichever playbook you are in, model in this order. Each layer links down to the next with plain
markdown path links, never `[[wikilinks]]`.

1. **Surfaces first.** One `screen` per composed GUI view, one `cli` per command-line app, one
   `server` per HTTP/WS service. The surface file is the **index** of its elements.
2. **Elements of each surface.** `component` (a UI part), `command` (a subcommand), `endpoint` (a
   route or WS channel). One-offs are `### id` **sections** under the surface's typed heading
   (`## Components` / `## Commands` / `## Endpoints`); anything reused, or large enough to outgrow
   a section, gets its **own file**, `detail:`-linked from the index.
3. **Behaviours.** `interaction` for a GUI event (click/hover/keyboard/drag/submit), `invocation`
   for a call or message (running a command, an HTTP request, a `ws-send`/`ws-push`). Sections
   under `## Interactions` / `## Invocations`. Each links `on:` its element and carries a `does:`
   nested-bullet effect list.
4. **Concepts.** Every durable noun the system is *about* — domain (`Worker`, `Diff`, `Gate`) or
   **code** (a function, class or module, carrying a `code:` bullet and no domain prose). Each
   `concept` gets its **own file** under `docs/features/<service>/concepts/` so others can link it.
   For an abstraction with implementations: model the base as a code concept, each implementation
   as a code concept that `extends:` it, and whatever *selects* one at runtime `refs:` the base.
   - **A concept is a real explanation, not a stub.** Cover its *parts* — a "Workflow" explains its
     states, transitions and inputs; a format explains its fields — and **point at the more
     specific node** for each: the format holding the on-disk shape, the code concept implementing
     a piece, the command that drives it. A one-line concept with a lone `code:` bullet is
     incomplete.
   - **State the key relations in the opening prose.** A file node's *graph* links are the ones in
     its intro region, before the first `##` subheading — that is what `ostler trace` surfaces and
     the linter checks. Put the relations you want discoverable there and elaborate in subsections.
5. **Flows.** A `flow` per multi-step journey; its `steps:` are an ordered list of links into the
   interactions, invocations and screens it traverses. Flows live at the service root (`flows/`),
   because a journey often crosses contexts.
6. **Formats.** A `format` per file or artifact shape (an `agents.yml`, an OpenAPI document), its
   fields as `### <key>` sections.

**Model breadth-first so links have targets** — scaffold the concept before the component that
`extends:` it, the endpoint before the interaction whose `does:` has `net:` into it. On a fresh
service the sequence that keeps links resolving throughout is: (1) concepts and any shared or
library components — the link *targets*; (2) surfaces with their element sections; (3) behaviours
linking `on:` those elements; (4) flows stitching the behaviours; (5) formats.

## Two completeness targets, not one

**Referential completeness** is the one doctor can see: every `on:` / `parent:` / `extends:` /
`detail:` / `steps:` link resolves and every required section and bullet is present — `ostler
doctor` green.

**Code-inventory completeness** is the other, and it matters most in the from-code playbook.
Reachable-from-the-root is necessary but not sufficient: entry-point descent alone misses
**siblings** and **non-entry modules**. Before you call a service done, diff the graph against the
source — every public class, module and function is either its own node or explicitly folded into
a documented behaviour or concept. Two blind spots to hunt deliberately:

- **Every implementation of an interface or ABC gets its own node**, not one example with the rest
  named in prose. A base with five subclasses is *five* sibling concepts, each with its own
  contract.
- **Library and utility modules the entry points never reach** — an SDK or a `scriptutil` imported
  only by other tooling — are still part of the book.

## Merging into nodes that already exist

A bulk build almost never lands on empty ground. Where a node is already there, the book-not-a-
changelog rule applies exactly as it does to a one-story merge: edit it until it describes the new
current reality completely. And when its `does:`/`raises:`/`states:` bullets carry no `verify:`,
**declaring them is part of the merge**, not optional polish — `undeclared-obligation` is queued
work you are standing on.

## The convergence gate

A service's subgraph is **done** when:

```bash
ostler fmt docs/features/<service>     # every file canonical (or: ostler fmt --check → exit 0)
ostler doctor                          # 0 errors
ostler list --type screen              # spot-check: the surfaces you expect are present
ostler trace <surface-root>            # from the cli/screen/server index — must reach every node
```

**No orphans.** Trace from the surface root and confirm you can walk to *every* node in the
subtree. A node nothing links to is an orphan — link it from the most relevant place: the surface
index's own intro region, the command whose flag drives it, the abstraction it `extends:`. Put
structural pointers in the node's bullets, not only in prose, so `trace` surfaces them.

Every doctor error names its own mechanical fix — casing and bullet order → `ostler fmt`; a
missing section or bullet key → `ostler scaffold` or add it by hand; a dangling link → fix the
target. The full table is [doctor-codes.md](doctor-codes.md). Never silence a finding by deleting
the bullet that carried the meaning. Loop until green.

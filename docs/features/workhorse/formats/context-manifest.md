# Context manifest

A per-repo JSON file, generated by farrier's install and committed to the consuming repo, that
[`workhorse-<name> run`](../workhorse.md#run)'s `--context-file` flag (or its auto-detect fallback) loads as
the *starting context* for a [workflow](workflow-format.md) run. Workflows now run **directly
from the prompt library** rather than being copied/rendered into the repo. The manifest gives a
library-resident prompt the repo's template variables and identity. Workhorse reads three of its
keys: `template`, `repo` and `vars`. Farrier also writes skill and prompt maps into the file, and
workhorse ignores them. A prompt finds an installed skill through the
[skill reference helpers](../concepts/template-globals.md), which read the harness folders on
disk instead of the manifest. `load_context_manifest` loads the file and parses it into a
`ContextManifest`. `build_manifest_context` projects that onto a `ManifestContext`, the run's own
value. Its `as_context()` lays the keys below under every turn, plus `_repo_root`. Its
`from_context()` reads `_repo_root` back at render time.

- file: `.agents/agents-context.json` (or a per-backend override, `.agents/agents-context.<AGENT_CLI>.json`)
- code: `workhorse/workhorse/manifest.py::load_context_manifest` @951a977f30ec
- code: `workhorse/workhorse/manifest.py::ContextManifest` @951a977f30ec
- code: `workhorse/workhorse/manifest.py::ManifestContext` @951a977f30ec

The loader's explicit-missing-file error and empty auto-detected-manifest behaviour are covered by
`workhorse/tests/test_context_manifest.py::test_explicit_missing_context_file_is_hard_error` and
`workhorse/tests/test_context_manifest.py::test_absent_auto_detected_manifest_returns_empty`;
the manifest's position as the outer layer of an agent turn is covered by
`workhorse/tests/test_pyflow.py::test_the_context_manifest_is_the_outer_layer_of_an_agent_turn`.

## Resolution

How [`run`](../workhorse.md#run) locates the manifest file, in order:

1. `--context-file <path>` given explicitly — used verbatim; the path **must** exist, or the run
   prints `error: --context-file not found: <path>` followed by a `Run \`make agent-install\` to
   generate .agents/agents-context.json.` hint, both to stderr, and exits `1`.
2. No flag — auto-detect under `$AGENT_REPO_DIR/.agents/` (`$AGENT_REPO_DIR` defaults to the
   launch `cwd`): first the per-assistant file `agents-context.$AGENT_CLI.json` (an unset
   `$AGENT_CLI` falls to the config's [`default_cli`](../concepts/config.md#resolve_default_cli), then
   to `claude` — the same order [`get_backend`](../concepts/get-backend.md) applies, so the manifest is
   detected for the CLI the run actually drives), then the generic `agents-context.json`.
3. Neither exists: the run proceeds with an **empty manifest** (`{}`). The run adds no manifest
   keys to any turn, so `template`, `repo`, `vars` and `_repo_root` are all absent. The skill
   helpers then resolve from the turn's `cwd`, else the process working directory. This is what
   lets a manifest-free workflow such as `hello-world` run with no repo context at all. A
   workflow that needs the manifest, such as `coder`, passes `--context-file` from its generated
   Makefile. A missing file there hits case 1's hard error instead of degrading to `{}`.

A file that exists but isn't valid JSON, or whose top level isn't a JSON object, is a hard error
(`error: cannot read context manifest <path>: <detail>` / `... must be a JSON object`) — exit `1`
either way, never a silent empty manifest.

## Fields

### field: template
- type: `map<string, any>`
- default: `{}`
- verify: json_path(path="$.template", matches="^\\{\\}$")
- required: false
- verify: json_path(path="$.template", absent=true)

Arbitrary key/value pairs from the repo's farrier `agents.yml` (`vars:`/`template:` blocks,
merged). Copied into the run's starting context verbatim under the `template` key, so a library
prompt reads `{{ template.<key> }}`.

### field: repo
- type: `map<string, any>`
- default: `{}`
- verify: json_path(path="$.repo", matches="^\\{\\}$")
- required: false
- verify: json_path(path="$.repo", absent=true)

Repo identity/metadata from `agents.yml`'s `repo:` block, plus `name` (defaults to the repo dir
name), `prefix` (the farrier install prefix), and `root` — pinned to the literal string `"."` in
the committed manifest (the install machine's absolute path is deliberately not recorded, to avoid
cross-machine drift; the agent's working directory is already the repo root at run time). Copied
into context verbatim under the `repo` key (`{{ repo.<key> }}`).

### field: vars
- type: `map<string, any>`
- default: `{}`
- verify: json_path(path="$.vars", matches="^\\{\\}$")
- required: false
- verify: json_path(path="$.vars", absent=true)

The same value as [`template`](#field-template) — farrier writes both keys so a prompt can use whichever
name it prefers. Copied into context verbatim under the `vars` key (`{{ vars.<key> }}`); distinct
from — and unrelated to — a workflow's own `vars:` block or [`run`](../workhorse.md#run)'s
`--params`/`--params-file`.

### field: instructions
- type: `map<string, string>`
- default: `{}`
- required: false
- semantics: farrier writes each selected skill's installed path here, and workhorse ignores the key
- verify: json_path(path="$._instructions", absent=true)

### field: instruction_tags
- type: `map<string, list<string>>`
- default: `{}`
- required: false
- semantics: farrier writes each selected skill's front-matter tags here, and workhorse ignores the key
- verify: json_path(path="$._instruction_tags", absent=true)

`find_by_tags` reads a skill's tags from its own installed front matter, not from this map.

### field: prompts
- type: `map<string, string>`
- default: `{}`
- required: false
- semantics: farrier writes each selected prompt's installed path here, and workhorse ignores the key
- verify: json_path(path="$._prompts", absent=true)

### field: used_skills
- type: `list<string>`
- default: `[]`
- required: false
- semantics: farrier writes the selected skill ids here, and workhorse ignores the key
- verify: json_path(path="$._used_skills", absent=true)

### field: skill_dir
- type: `string`
- default: `""`
- required: false
- semantics: farrier writes the skills directory it installed under here, and workhorse ignores the key
- verify: json_path(path="$._skill_dir", absent=true)

A manifest written before the skill reference helpers carries these keys, and an older run read
them. `ContextManifest` ignores every key it does not declare, so such a manifest still loads. The
render context never holds `_instructions`, `_instruction_tags`, `_prompts`, `_used_skills` or
`_skill_dir`.

- tests: `workhorse/tests/test_context_manifest.py::test_the_skill_maps_of_an_older_manifest_stay_out_of_the_context`

## Runtime mapping

`load_context_manifest` parses the file (see [Resolution](#resolution)) into a `ContextManifest` —
tolerantly, so an unknown key is ignored and a wrong-typed one falls back to its default rather
than ending the run. `build_manifest_context` then projects it onto a `ManifestContext`. The
projection keeps each non-empty `template`, `repo` and `vars` map. It adds `repo_root`, the
resolved absolute `$AGENT_REPO_DIR`, else the launch `cwd`. The manifest file does not store it.
The flavor-override lookup reads it. A turn with no `cwd` of its own resolves skills from it.
`ManifestContext.as_context()` turns that value into context keys, and it alone spells
`_repo_root` when writing.

**It lives outside the driver because it is a property of the run, not of the machine.** A
[Python state machine](../workhorse.md) takes those keys on its `RunEnv` and lays them *under*
every agent turn's arguments. A state that binds `repo` gets its own, and the skill helpers
resolve either way. An empty manifest adds no keys at all, so a manifest-free run renders exactly
the arguments its state passed. (The retired YAML engine instead seeded the same dict as the run's
starting context; that is the only difference the removal made, and it is why the loader was never
part of either front end.)

Farrier writes one manifest per backend it renders, `.agents/agents-context.<backend>.json`. The
loader picks the one for the active `$AGENT_CLI` when no `--context-file` names another.

## Methods

### method: ContextManifest.project
- sig: `ContextManifest.project(*, repo_root: Path) -> ManifestContext`
- does: keep each of `template`, `repo` and `vars` that is not empty
- verify: json_path(path="$.template", absent=true)
- does: resolve `repo_root` to an absolute path
- verify: count(subject="relative repo roots in a projected manifest", equals=0)
- returns: a `ManifestContext` marked present
- verify: json_path(path="$.present", equals=true)
- code: `workhorse/workhorse/manifest.py::ContextManifest.project` @951a977f30ec
- tests: `workhorse/tests/test_context_manifest.py::test_build_manifest_context_names_what_it_read`

### method: ManifestContext.as_context
- sig: `ManifestContext.as_context() -> dict[str, Any]`
- does: return an empty mapping for the manifest-free case
- verify: count(subject="keys a manifest-free run adds to a turn", equals=0)
- does: emit the kept values and the reserved `_repo_root` key when present
- verify: json_path(path="$._instructions", absent=true)
- returns: the context layer merged underneath every agent turn's arguments
- verify: json_path(path="$.present", equals=true)
- code: `workhorse/workhorse/manifest.py::ManifestContext.as_context` @951a977f30ec
- tests: `workhorse/tests/test_context_manifest.py::test_an_absent_manifest_adds_no_context_key`, `workhorse/tests/test_context_manifest.py::test_the_reserved_keys_round_trip_through_one_type`

### method: ManifestContext.from_context
- sig: `ManifestContext.from_context(context: Mapping[str, Any]) -> ManifestContext`
- does: read `_repo_root` from an already-merged render context
- verify: count(subject="repo roots read back from a render context", equals=1)
- does: mark the manifest present when the context holds `_repo_root`
- verify: json_path(path="$.present", equals=true)
- returns: a tolerant `ManifestContext` value that carries no template, repo or vars values
- verify: count(subject="values carried by a context read back", equals=0)
- code: `workhorse/workhorse/manifest.py::ManifestContext.from_context` @951a977f30ec
- tests: `workhorse/tests/test_context_manifest.py::test_the_reserved_keys_round_trip_through_one_type`

### method: build_manifest_context
- sig: `build_manifest_context(raw: dict[str, Any], *, repo_root: str | None = None) -> ManifestContext`
- does: validate raw manifest data with tolerant defaults and ignored unknown keys
- verify: json_path(path="$._skill_dir", absent=true)
- does: resolve an omitted repo root from `AGENT_REPO_DIR`, else `.`
- verify: count(subject="repo roots on the projected context", equals=1)
- returns: the `ManifestContext` that `ContextManifest.project` gives for the parsed data
- verify: json_path(path="$.present", equals=true)
- code: `workhorse/workhorse/manifest.py::build_manifest_context` @951a977f30ec
- tests: `workhorse/tests/test_context_manifest.py::test_build_manifest_context_names_what_it_read`, `workhorse/tests/test_context_manifest.py::test_a_wrong_typed_field_degrades_instead_of_raising`

### method: load_context_manifest
- sig: `load_context_manifest(context_file: str | None) -> ManifestContext`
- does: load an explicit file or select the active-CLI-specific then generic auto-detected manifest
- does: return an absent `ManifestContext` when no auto-detected manifest exists
- raises: `SystemExit(1)` after reporting an explicit missing file, unreadable JSON, or non-object top level
- returns: the projected context for a valid manifest
- verify: exit_status(code=1)
- code: `workhorse/workhorse/manifest.py::load_context_manifest` @951a977f30ec

## Sample

Farrier writes every key below. Workhorse reads only `template`, `repo` and `vars`.

```json
{
  "template": { "team": "platform" },
  "repo": { "name": "acme-api", "prefix": "acme", "root": "." },
  "vars": { "team": "platform" },
  "instructions": {
    "coder-workflow": ".claude/skills/acme-coder-workflow/SKILL.md"
  },
  "instruction_tags": {
    "coder-workflow": ["backend", "standards"]
  },
  "prompts": {
    "story-plan": ".claude/commands/acme-story-plan.md"
  },
  "used_skills": ["coder-workflow"],
  "skill_dir": ".claude/skills"
}
```
